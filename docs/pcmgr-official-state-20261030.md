# PCMgr 官方持久状态与当前恢复差异

2026-10-30。用户实测官方客户端无需重扫，仍能打开小程序的已登录业务页面；本项目同日新授权的延时取码失败。两者确有可用性差异，不能把官方主账号、业务后端缓存 token、WMPF 会话和独立恢复密钥当成一个状态。本文记录已核对的代码与实验边界，尚未确认持续失效的共同根因。

## 当前结果

| 对照 | 结果 | 能说明什么 |
| --- | --- | --- |
| 正式 v0.2.52 新授权即时实验 | ManualAuth、独立新连接 AutoAuth、密钥轮换和取码通过 | 解析和请求至少在这次新会话成立 |
| 正式授权延时恢复 | 应用层 `-14`，独立 AutoAuth 业务 `-13` | 延时恢复仍失败，不是长期修复 |
| 官方客户端由用户打开小程序 | 无需重新扫码，已登录业务页面可加载 | 官方业务仍可用，需继续核对其实际 WMPF / 业务缓存层 |
| 同期官方 DLL 使用当前主账号 key 获取 `20138` | 业务 `1`，没有 buffer | 只复制当前主 key 的取票据路径仍不足，不能据此声称官方小程序也不可用 |
| `QMReadConfig` 与 common-config getter | 公共配置合并授权值为 1，没有读到临时 token | helper 的版本专用配置对象未初始化，不能排除官方进程的版本专用或运行时状态 |

没有再次消费已尝试 AutoKey，没有修改正式扫码时间、真实到期时间或官方配置。主 key 续期成功、名义 PSK 到期很远、数据库状态 `alive` 均不能代替真实业务成功。

## 当前 V3 的真实调用者

样本 `Qt64/MAL.exe` SHA256：`ce4b4acd5b7b472819f98eb321eedd44d9a4aa15b81f2ad85e5c50d791bd55bb`。

| 分支 | 静态证据 |
| --- | --- |
| 需要登录参数 | `OnAppletGetLoginParams`，`0x1526ad` 调 `AppletLogin` `0x46050` |
| 已有登录 buffer | `AppletLogin` 将其交给 runtime 的 ThirdPartyLogin |
| 无 buffer、有临时 token | `0x462ac` 检查缓存，`0x463ce` 调 `0x47eb0`；该函数以 GUID + token 发 `20138` |
| 无 buffer、合并授权开启 | 上报事件 18；`OnWmpfMergeAuth` 的 `0x157941` 调 `0x47420`，以主账号 key / GUID、空 authcode 发 `20138` |
| 无 buffer、需额外授权 | 上报事件 16；`OnPullWmpfLogin` `0x156180` 分发 `miniappsdk_showauth` / `auth_code_mal`，不等同于轮换主 key |
| runtime 报需要 AutoLogin | `0x6c648..0x6c6d2` 与需要 ManualLogin 的分支共同调用 `HandleManualLogin` `0x69ba0`；代码旁明确标记 `AutoLogin disabled` |

这一层禁用自动登录不代表底层 ILink 没有 AutoAuth 实现。它说明“底层可构造 AutoAuth”与“当前官方 V3 实际这样恢复”不同。本项目已实现的 AutoAuth 不能单凭名字认作完整复刻官方策略；先前即时成功、延时失败的结果均保留。

MAL 中的 `GetLoginCodeReq` 目前只追到生成的 protobuf 序列化器、虚表、构造器与 descriptor 默认对象，尚未找到可确认的业务发送点。日志中的 “request login_code” 也不能替代真实调用者证据，不猜测未确认的命令号。

可复核的静态检查：

```powershell
python tools/inspect_pcmgr_login_flow.py 'C:/path/to/Qt64/MAL.exe'
```

该工具固定核对样本与五条实际 call 边，仅离线读取程序文件，不读取用户配置、注入进程或访问网络。

## 环境匹配仍缺什么

### PC 微信参与启动：用户对照与静态证据

用户进一步观察到：打开官方小程序前 PC 微信窗口会短暂闪现；退出 PC 微信后，YYB 与 PCMgr 都无法打开该小程序，YYB 面板还立即表现为掉线。这是用户现场对照，尚未采集对应时刻的网络 / 进程事件，不能直接断定退出操作撤销了哪一种服务端凭据。

用户随后明确该操作是**退出程序 / 结束进程，保留登录记录**，并非“退出登录”。因此先检查本地启动和 IPC / SDK 状态依赖；只有看到对应服务端明确拒绝，才能进一步判断凭据是否被撤销，不能仅凭 UI 变化推断全局 OAuth 失效。

当前 PCMgr 样本存在明确的替代启动通路，已核对实际指令，而非只搜索到字符串：

| 位置（MAL RVA） | 已确认的操作 |
| --- | --- |
| `0x14a7f0..0x14b54f` | `HandleLaunchAppletByWeChat` 检查目标 AppID 配置、scheme 支持、PC 微信登录和 WMPF 登录状态 |
| `0x14e96e..0x14ea3b` | 启动入口先调用该通路；成功在 `0x14e975` 跳过后面的 WMPF 登录检查，失败才调用 `0x46bc0` 检查 WMPF |
| `0x14adee..0x14ae02` | 仅当 scheme 支持、PC 微信已登录、WMPF 未登录时进入替代通路；三个相反条件均跳转 `0x14b364` 回到 WMPF 分支 |
| `0x14afe5..0x14b014` | 构造 `weixin://dl/business/?appid=` 加目标 AppID |
| `0x14b0e2 → 0x156d0` | 通过 `QMOpenURL` 打开该 URI，由桌面微信处理 |
| `0x14b161..0x14b1ca` | URI 启动成功后进入 `OnLaunchAppletByWeChat`；日志明确为 `skip WMPF login check` |
| `0x14e17f → 0x14cc60` | 另一个 AMS 启动入口也检查 PC 微信登录，再调用 SDK 启动 |
| `0x14fd5d` / `0x14fe30` | 窗口恢复处理通过 `PostMessageW` 发送最小化 / 关闭到托盘消息；与闪现后隐藏现象相符，但没有证明本次具体走了哪条分支 |

因此官方“仍可打开业务页面”至少还存在一种解释：在独立 WMPF 未登录时借助 PC 微信自己的登录态启动，而不是原独立凭据已经续期。它与额外授权 code 换新 buffer 是两条不同通路，不能混为一谈。该发现推翻了“官方能打开就一定保持同一独立会话”的前提，但没有否定现场观察，也没有证明所有 AppID 都走桌面微信。

YYB `5.10.7600.6722/AndrowsStore.exe` 也已找到独立的 `WXApplet::LaunchWXAppWithSchema`：`0x177c28` 读取 `url_scheme`，`0x177da7` 检查空值，非空值交给异步回调 `0x1780c0..0x17831f`；该回调在 `0x178114` 调导入的 `ShellExecuteW`，`0x178175` 按 Windows 返回值大于 32 判断启动成功。成功日志中的 `code` 是 ShellExecute 返回值，不能当作 `wx.login` code。这确认 YYB 也有 OS scheme 启动机制，但尚未采集本次实际 URI / 分支，不能声称这一次一定使用该函数，或认定退出 PC 微信就必然撤销 YYB OAuth。

该 YYB 样本 SHA256 为 `dc32d301e15e7e7ed8e5de5ec03067f1b031f6e7333b28bc3adb3703084d9727`；只读安装文件分析，没有执行退出、修改配置或抓取私人消息。

飞牛 Docker 当前没有桌面微信 / URI handler，也没有实现将该通路的会话安全转交给服务端；添加同名开关、修改设备字段或保持 TCP 连接均不能实现这种替代启动。下一步应分别验证桌面微信启动、额外授权 code 换票据、现有 ILink 恢复的边界。YYB 与 PCMgr 的调用点分别核对，不互相套用 RVA 或认定实现完全相同。

离线核对工具现同时校验上述 URI 调用、成功回调和三个条件分支；不拉起或退出客户端，不消费真实凭据。

可选再传 `--yyb-binary 'C:/path/to/AndrowsStore.exe'`，同时核对固定 YYB 样本的 `ShellExecuteW` 导入调用和返回值判定。

- 官方保留的持久设备、runtime 会话、临时 token 与版本配置，需要按各自作用域核对，不能把一个字段复制成所有设备标识。
- 本项目保存 WMPF / PSK / 独立恢复密钥，但登录完成后关闭该条长连接。官方保持原生 runtime 生命周期；尚无对照实验能证明仅保持连接或增加传输心跳就会延长应用授权。
- 当前额外授权分支尚未得到新授权 code / 返回 token 的完整真实闭环。没有重放历史 code，也没有把猜想分支接入正式扫码。
- 官方已登录业务页可能复用业务后端 token，是否同时发生新的 `wx.login` 仍需独立事件证据。用户实测保留为有效业务可用性证据，不把该限制用来否定现场结果。

## v0.2.53 观测补齐

管理员左侧“运行日志”记录服务、面板登录、管理操作、账号扫码 / 失效、接口、后台续期和协议恢复事件，可按分类、等级、账号、渠道、时间筛选。独立密钥恢复、取新票据、退避和候选验证分别记录，避免再次仅凭一条失败猜调用流程。

修复 PCMgr 错误链遗漏：`RPCError(20138)` / `BufferRejectedError` 归为 `pcmgr_login_buffer`，`RPCError(20042)` 归为 `pcmgr_key_renewal`。已确认的上游数值码不再只留在错误文本中；这修复可观测性，不宣称上游拒绝已解决。

日志仅写入固定事件及受限结构字段，不收集原始错误正文、HTTP body / query、账号身份、凭据或扫码链接。异步有界队列落 SQLite，重启可读，保留近 7 天且最多 10,000 条；队列溢出会记录丢弃数，不阻塞协议调用。需要管理员登录，普通用户与匿名访问均被拒绝。升级前历史不会伪造回填。
