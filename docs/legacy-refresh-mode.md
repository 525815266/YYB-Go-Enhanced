# AS 默认历史刷新策略（v0.2.57）

**已知问题：原默认按来源刷新策略已有延时失效记录，当前尚不能保证长期保活。** v0.2.56 仅提供可选兼容项；v0.2.57 起默认使用 `legacy_auth`，无需另开开关。兼容路径已有即时刷新和取码正向结果，但这不足以认定长期问题已解决。

早期 Docker 隔离样本在扫码约2小时、4小时后的两次预定取码均返回HTTP200和32位code。第二次请求自身更换票据、重建会话并延长本地凭据期限；全程没有后台续期记录。存在手动及额外业务请求干预，不能称为自然后台续期成功。完整记录见[早期版本审计](unversioned-docker-audit-20261031.md)。

## 合入的差异

| 路径 | 显式回退 `source`（v0.2.56 的默认值） | `legacy_auth`（v0.2.57 起默认） |
| --- | --- | --- |
| AS 主登录凭据刷新 | 按原来源选择主刷新；含糊拒绝按既有规则补check-login | 直接使用 `/pc_yyb_auth/pcyyb_refresh_token_auth`、`pc_yyb_auth` 业务及对应签名 |
| AS 独立授权刷新 | 原 `_auth` 路径 | 同一 `_auth` 路径 |
| PM 续期 | 独立原生key续期 | 仍为独立原生key续期 |
| 保存票据与候选会话 | 沿用v0.2.55保存票据优先恢复 | 相同；明确票据access拒绝触发的凭据刷新改用历史入口 |

模式同时作用于后台、手动刷新和现有业务恢复中的凭据刷新。它不在同一次失败后遍历两个刷新入口，也不将一个渠道的票据放进另一个渠道。来源标记保持原样，切回默认模式即可恢复原有路由，不需要迁移账号或重新扫码。

继续保留严格数值响应码、账号匹配、代理及直连回退策略、取消请求保护、先保存轮换再取票据、并发扫码CAS和授权 / 会话分层。未恢复“每逢缓存缺失先强刷”的旧行为，也未缩短可用PSK期限以制造更多握手；后台频率和提前量沿用现有配置。当前缺省有效期及同token响应仍只作为本地调度材料，不能用来证明上游真实延寿。

## 为什么旧版能继续取码，新版仍出现失效

已确认差异与推断分开记录，完整阶段见[旧版审计](unversioned-docker-audit-20261031.md)和[新版首次失败](code-recovery-20261031.md#本轮终止自然拒绝后的恢复仍失败2026-10-31)。

| 对比项 | 7月31日原版 | v0.2.55 / v0.2.56 原默认策略 | 解释与本次处理 |
| --- | --- | --- | --- |
| AS 刷新入口 | 带签名的 `_auth` | 主扫码来源走主刷新，含糊 `-109` 后可能补 check-login | 真实请求路径不同；v0.2.57 默认改为 `_auth`，仍需长期验证 |
| 协议缓存缺失 / 重建 | 先强刷凭据、取票据再握手；旧版会话缓存较短 | 保存票据优先；明确 access 拒绝才允许凭据刷新 | 旧样本18:04、19:07、20:13的业务请求可触发按需刷新，不能把随后可用归因于后台；本次不恢复无条件强刷或缓存截断 |
| 后台窗口 | 每30分钟检查，提前45分钟 | 通常每2分钟检查，直连提前4分钟；代理按账号设置 | 旧样本反复按需推后期限，后台成功 / 失败均为0，无法据此证明旧后台策略优于新版 |
| 首次失败时间 | 本轮约4小时后仍可取码，但请求自身重建 | 新版13:27:19扫码、14:08:07首次完整失败，约41分钟；原正常窗口15:22:18 | 新版在后台窗口前就失败，仅调整后台周期不能解释或解决这次拒绝 |
| 失败阶段 | 本轮取码成功 | `shortlink_application -14` → `manual_auth -10` → `login_buffer -101 / 42007` → `refresh_token -109` 与 `check_login -109 / 42007` | 会话、票据与凭据恢复分别遭拒；14:16出现的 AutoAuth `-13` 晚于首次失败，不能作为14:08的原因 |
| 成功判断 | 宽松响应码转换、缺省7200秒本地重算 | 严格数值码、账号匹配；同token缺省期限仍仅用于本地调度 | 离线虚构响应可复现旧解析误判，但没有证据称真实服务端发过该响应；不恢复宽松判定 |

可确认的直接事实是新版那份授权的业务与恢复材料被上游拒绝；尚不知道上游拒绝的唯一触发原因。两轮虽然同飞牛出口，但扫码授权、请求时间线和实现不完全相同，且旧样本有手动 / H5 / 额外业务干预，不构成同授权单变量对照。因此默认改为有正向兼容线索的入口是可回退的工程调整，不是已证明的根因修复。没有证据认定用户任务、渠道混用或某一次后续握手导致首次失败。

## 启用与还原

v0.2.57 起，未设置或留空即使用 `legacy_auth`。Docker Compose、原生程序和 Magisk 的新配置示例均默认启用。也可在 `.env` 或 Magisk 的 `/data/adb/yyb-go/config.conf` 显式设置：

```dotenv
YYB_APPSTORE_REFRESH_MODE=legacy_auth
```

**已有 v0.2.56 配置显式写了 `source` 时，升级程序不会覆盖用户配置。** 删除该项或改为 `legacy_auth` 后重启；若自定义 Compose 直接写死 `source`，也需修改对应环境项。Compose需重新创建容器以更新环境变量；原生程序支持已有 `-env-file` 参数。要回退按来源刷新则显式设置 `YYB_APPSTORE_REFRESH_MODE=source`。其他值会在打开数据库前报错，不会静默切到某条路由。启用后台检查时，启动日志的 `appstore_refresh=legacy_auth` 可确认实际模式。

该设置在当前实例的有效AS账号上统一生效，不改变账号ID、扫码渠道、扫码时间或已失效账号状态。PM账号不受影响。没有复活旧账号、恢复失败密钥或改写真实到期时间的操作；新授权仍需用真实后台记录和原期限后取码验证。

## 验证边界

v0.2.56 源码通过全量 Go 测试、`go vet`、Release 说明测试及 Windows / Linux amd64 原生启动检查，内嵌首页、扫码页和匿名协议鉴权检查均通过。旧样本已停止的原库仅用于 SQLite 只读备份；新程序在另一个独立目录运行，后台关闭，结束后停止进程，没有重启历史容器或操作正式账号。

独立副本第一次 `/accounts/refresh` 因尚未进入窗口而直接返回，本地凭据未变，随后控制取码 HTTP200 / code32，不能算作刷新实测。第二个独立副本仅将进程刷新提前量设为3小时、保持后台关闭和原到期值，单次手动检查进入 `_auth` 刷新：HTTP200、状态 alive、无刷新错误，本地期限延长，access / refresh、身份、扫码时间、票据及会话均不变；随后一次控制取码 HTTP200 / code32。原库缺省来源字段在新库序列化为空字符串，语义仍为空，未标记为另一来源。原始响应及进程日志仅留私有记录。

这是对既有授权的受控即时兼容性验证；同token及本地期限延长不能证明服务端真实延寿，也没有提供无人干预跨期限或长期后台续期结论。

v0.2.57 的默认值变更通过全量 Go 测试、`go vet` 和发布说明测试；Windows 实际启动分别验证“未配置”“空值”均记录 `appstore_refresh=legacy_auth`，显式 `source` 仍记录 `source`，三个实例的页面、健康和鉴权检查均通过。测试未向真实账号追加刷新或取码；此次发布不新增长期保活结论。

旧版按需刷新 / 重建已提供正向线索，当前合入的是可明确选择、可还原的刷新路径，不是已证明能解决全部延时失效的默认策略。新版本没有自动重启已结束的历史观察容器，也没有把两次历史取码换算成自然续期轮数。
