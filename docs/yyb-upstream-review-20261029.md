## 本次已修复的缺陷

此前 `intFromAny` 对不认识的类型返回 `0`，并把浮点数直接截断。模拟上游响应确认：字符串 `"42007"`、缺失 `code` 和 `0.5` 等，在同时携带 token / buffer 时，会进入成功分支。即使实际错误响应通常没有可用载荷，也可能丢失真正的业务错误码，甚至误接收附带数据。

v0.2.41 保留原始 JSON 错误码，仅接受 32 位整数或可解析的整数字符串：

- `0` / `"0"` 才允许继续检查成功载荷。
- 非零整数保留 `LoginBufferRejectedError` / `RefreshRejectedError` 与 `refresh_token` / `check_login` 阶段，继续走现有诊断与失效判断。
- 缺失、null、布尔、对象、小数、指数、非法字符串和越界整数按格式异常返回；不伪造业务错误码，不因为格式异常直接删除账号凭据。
- 错误消息不回显非法字段或响应载荷；不增加网络重试。

测试先在原实现复现，再覆盖取登录票据、刷新、check-login 三个真实客户端入口。正常数值响应、整数字符串成功、业务拒绝、脱敏与请求次数一起验证。

## 尚未解决的问题

截至本次检索，没有找到可复核的证据证明相关开源实现已恢复长期保活或解决 30 天内快速失效。`yyb-auth-service` 的新修补仍使用 `_auth` 刷新；不能用其提交标题替代官方主登录凭据来源的分析，也不能把其短时成功当作本项目持续运行结果。

其他使用应用宝接口的项目也有同类反馈，例如 [QQ-Farm-Bot 的 -109 / RC_PARAMS_INVALID 报告](https://github.com/XooUooX/QQ-Farm-Bot/issues/1)，但该报告没有进一步诊断和解决方案。它只能证明存在相同错误现象，不能证明共同根因。

后续保留真实到期时间，验证后台续期、原到期后取码及下一轮续期。官方存在网络内部 `AppDeviceId` 和 TDI 应用 `kTdiKeyDeviceId` 两条设备分支，后者也会持久保存 32 原始随机字节，不能混用默认长度。用户授权当前账号隔离实验后，已将额外握手记为观察干预；ManualAuth 取码通过，但 AutoAuth 候选仍被拒绝，见[调用链复核](native-keepalive-audit-20261028.md#ilink-设备标识的进一步定位)及[隔离实测](native-wire-layout-20261029.md#2026-10-29-隔离-autoauth-验证)。未经验证，不修改生产握手字段或增加猜测心跳。

本次参考实现思路并独立编写代码；`yowiv08/yyb-auth-service` 在核查时未提供许可证，未复制其源码。
