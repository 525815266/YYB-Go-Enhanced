# 授权稳定性：已有措施与验证边界

账号授权可能被上游拒绝，之后需要重新扫码。这个问题的根因仍在排查：**项目没有任何已验证的办法保证授权长期不掉线，也没有验证过 30 天保活。** 本文只做三件事：列出已有的防护与诊断措施，说明每一项能做什么、不能做什么，并收录原先写在项目首页的按版本记录。

> 这些措施是**流量控制和诊断手段，不是修复**，不能恢复已被微信撤销的授权。默认值是保守的起点，不是测出来的安全值；它们是否有效，需要在重新扫码的账号上继续观察。

## 已有措施

- **固定设备标识**（v0.2.58）：每个账号固定一套协议设备，不再每次握手、每个请求都换新的随机设备。开关：`YYB_DEVICE_IDENTITY=stable`，`random` 恢复旧行为。详情：[配置](configuration.md#协议设备标识v0258-起)、[取证与验证边界](device-identity-offline-notify-20261101.md)。
- **历史刷新策略**（v0.2.57 起默认）：AS（YYB 渠道）默认使用历史 `_auth` 刷新入口；PM（PCMgr 渠道）独立续期不变。开关：`YYB_APPSTORE_REFRESH_MODE=legacy_auth`，`source` 回退。详情：[问题对比与配置说明](legacy-refresh-mode.md)。
- **授权与会话分层**（v0.2.50 – v0.2.55）：OAuth 拒绝与协议会话分开处理，授权被拒但仍有可尝试的材料时显示“需补授权”，不再把两层一起清空。无开关。详情：[分层处理说明](credential-session-layers.md)。
- **会话保护**（v0.2.60，v0.2.61 加固）：会话刚验证成功后，单个 AppID 的 `-14` 不再触发重新登录（2 分钟内）。开关：`YYB_FRESH_SESSION_WINDOW=2m`（v0.2.65 起），`off` 或 `0` 关闭；批量取码被拦得太多时见[取码量对照实验](dense-batch-lab-20261103.md)。详情：[v0.2.60 与 v0.2.61 各做了什么](code-pacing-20261102.md#v0260-与-v0261-各做了什么)。
- **取码熔断**（v0.2.59）：对反复被应用层拒绝的取码返回本地 `429`，不再继续冲击上游；不改账号状态、不清凭据。开关：`YYB_CIRCUIT_BREAKER=on`，`off` 关闭。详情：[配置](configuration.md#取码熔断v0259-起)、[取码熔断与触发规律](code-circuit-breaker-20261101.md)。
- **登录预算**（v0.2.61）：同一账号因业务请求触发的重新登录和强制刷新在窗口内有次数上限，用完后请求保持原来的错误、不再向上游登录。开关：`YYB_LOGIN_BUDGET=3`、`YYB_LOGIN_WINDOW=10m`，`off` 或 `0` 关闭。详情：[配置](configuration.md#登录预算与取码限速v0261-起)、[任务高峰、重新登录与登录预算](code-pacing-20261102.md)。
- **取码限速**（v0.2.61）：同一账号向上游发出的取码 / 取号 / operateWxData 请求至少相隔一段时间，排不进的返回本地 `429`。开关：`YYB_CODE_MIN_GAP=3s`、`YYB_CODE_MAX_WAIT=20s`，`0` 或 `off` 关闭。详情同上。
- **网站应用 AppID 保护**（v0.2.63）：取码请求带着已知的网站应用 AppID（腾讯电脑管家、京东护照）时返回本地 `403`，不发往上游。开关：`YYB_CODE_ALLOW_APPIDS` 放行、`YYB_CODE_DENY_APPIDS` 追加。详情：[网站应用 AppID 取码与授权失效](website-appid-getcode-20261103.md)。
- **运行时调参**（v0.2.61）：数据库目录里的 `tuning.json` 不重启覆盖登录预算、限速数值与会话保护窗口，一秒内生效，默认没有该文件。详情：[配置](configuration.md#登录预算与取码限速v0261-起)。
- **掉线通知**（v0.2.58）：授权被拒、需要重新扫码时推送一次提醒。开关：`YYB_NOTIFY_CHANNEL` 留空则关闭管理员渠道。详情：[配置](configuration.md#掉线通知v0258-起)。
- **运行日志**（v0.2.53）：记录续期、票据、原生恢复、熔断、限速等事件，保留近 7 天、最多 10,000 条，在管理员「运行日志」页查看。详情：[控制台说明](console-features.md#运行日志)。

`tuning.json` 可调整的键有 `login_budget`、`login_window_ms`、`code_min_gap_ms`、`code_max_wait_ms`；缺少的键沿用配置值，文件无法解析时保留上一次有效设置，删除文件恢复配置值。登录预算与取码限速的开关和数值见[配置与账号安全](configuration.md#登录预算与取码限速v0261-起)。

## 它们不能做什么

- 不能恢复已被微信撤销的 refresh token，也没有验证 30 天保活。
- 熔断、登录预算和限速只控制发往上游的流量：熔断只统计失败，登录预算只统计 OAuth 层调用，一个全部成功的突发它们拦不住，限速补的就是这个缺口。限速的默认值依据少量观察得到，是保守的起点，没有对照实验证明它能阻止授权被吊销。
- 登录预算的上限在文档记录的两轮对照回放里一次都没有被触及，也没有证据表明它带来了额外保护；默认是否开启取决于后续观察，详见 [任务高峰、重新登录与登录预算](code-pacing-20261102.md)。
- 有代价：高峰里需要重新登录的 AppID 会失败，直到窗口滑过；一个账号在 20 秒的排队窗口里最多排进约 7 个请求，其余收到本地 `429`。

## 脚本侧能做什么

- 把青龙里**同一账号**的任务错开启动时间，不要让大量任务挤在同一分钟；[登录预算文档](code-pacing-20261102.md)的建议是相隔 3 到 4 分钟以上，依据是代码里的会话保护窗口等常量，不是测出来的安全值。
- 停用桥接脚本、用公众号取小程序 code 的脚本；收到本地 `429`（带 `Retry-After`）时按间隔退避，它与上游 `502`、需要重扫的 `409` 含义不同。详见 [取码熔断与触发规律](code-circuit-breaker-20261101.md) 和 [代理与账号保活](proxy-keepalive.md#scan-first-call-409)。

## 怎样确认是否生效

重扫账号后，让它经历一次青龙的高峰，然后看运行日志：

- `protocol.login_limited`：预算是否在挡登录，次数多大；
- `protocol.paced`：限速是否在排队或拒绝请求，一个突发里有多少；
- `protocol.recovery_started` / `ticket_requested`：窗口里的登录有没有超过预算；
- `account.expired`、`keepalive.failed`：授权是否仍然被拒；
- 账号状态是否仍为可用，到期时间是否继续往后移。

如果账号在限速和预算内仍然失效，说明登录次数不是唯一原因，需要根据带 `app_id` 的事件继续缩小范围。完整方法见 [任务高峰、重新登录与登录预算](code-pacing-20261102.md#怎样验证)。

## 按版本的记录

以下段落原先写在项目首页 README，按版本从新到旧整理；文字保持原样，仅调整了相对链接和小标题。完整更新记录见 [CHANGELOG](../CHANGELOG.md)。

### v0.2.61：登录预算与取码限速

v0.2.61 新增[登录预算](code-pacing-20261102.md)（`YYB_LOGIN_BUDGET` 默认 `3`、`YYB_LOGIN_WINDOW` 默认 `10m`，可在数据库目录放 `tuning.json` 不重启调整）：同一账号因业务请求触发的重新登录和强制刷新有次数上限，用完后请求保持原来的错误、不再向上游登录。依据是一次高峰回放：约 150 秒内 38 次登录票据就让一个健康授权被拒，旧版代码同样 3.5 分钟内死亡，而没有任务触达的授权连续续期成功。同时加固 v0.2.60 的“会话刚验证成功”防护，并默认限制同一账号向上游发出请求的间隔（`YYB_CODE_MIN_GAP` 默认 `3s`）：正式环境里有一个授权在 7.5 秒内连续成功取到 12 个 code 后被每一层拒绝，熔断和登录预算都管不到成功的突发。这是流量控制，不保证授权不再被吊销，默认值是保守起点，尚待重扫账号后验证。

### v0.2.59 – v0.2.60：取码熔断、调用日志与整点相关性

v0.2.59 新增[取码熔断](code-circuit-breaker-20261101.md)（`YYB_CIRCUIT_BREAKER`，默认 `on`）：对反复被应用层拒绝的取码返回本地 `429`，不再继续冲击上游。v0.2.60 起运行日志记录被拒的 AppID 与请求类型，会话刚验证成功时 `-14` 不再触发重新登录，熔断按请求类型区分。后续统计发现新授权几乎都在偶数整点的批量取码之后失效，v0.2.58 取证里的“43 / 82 分钟”并非授权寿命，相关性与对照方法见[整点任务与新授权失效](hour-mark-offline-20261101.md)（因果尚未验证）。

### v0.2.58：固定设备与掉线通知

v0.2.58 默认**每个账号固定一套协议设备**（`YYB_DEVICE_IDENTITY=stable`），不再每次握手、每个请求都换新的随机设备；修复 legacy 模式下失效账号停在 `unknown` 并每 2 分钟重试的问题；新增[掉线通知](configuration.md#掉线通知v0258-起)，授权被拒需要重新扫码时推送到管理员渠道和账号自己的推送渠道。正式环境取证显示授权在续期窗口前已被上游拒绝，本版不宣称长期保活已解决，见[取证与验证边界](device-identity-offline-notify-20261101.md)。

### v0.2.57：默认启用 `legacy_auth` 历史刷新策略

v0.2.57 起 AS **默认启用 `legacy_auth` 历史刷新策略**，无需另开开关；PM 独立续期不变。原默认策略已有延时失效记录，兼容路径目前仅验证即时刷新与取码，长期保活仍未证实。已有配置显式写了 `YYB_APPSTORE_REFRESH_MODE=source` 时需删除该项或改为 `legacy_auth`，Docker 更新后需重新创建容器；显式 `source` 仍可回退。见[问题对比与配置说明](legacy-refresh-mode.md)。v0.2.56 首次引入该兼容策略，当时默认未开启。

### v0.2.55：恢复同渠道保存票据优先的取码重建

v0.2.55 针对回退 v0.2.49 后恢复取码的反馈，恢复同渠道保存票据优先的取码重建路径；候选取码成功后才替换共享缓存，明确的新票据 access 拒绝才允许一次凭据刷新。失败按目标退避，成功不再阻塞后续恢复。保留渠道隔离与并发授权保护；已清空的授权需重新扫码，长期续期仍未验证，见[恢复顺序与验证边界](code-recovery-20261031.md)。

### v0.2.53：运行日志与 PCMgr 错误链

v0.2.53 在管理员左侧新增“运行日志”，支持分类、等级、账号、渠道和时间筛选，可查看续期、票据、原生恢复及调用的独立事件。日志重启保留，近 7 天最多 10,000 条，不采集密钥或请求正文。补齐 PCMgr 票据 / 主 key 错误链，并记录[官方持久状态与当前恢复差异](pcmgr-official-state-20261030.md)；延时原生恢复仍有失败，另有按需新票据恢复成功样本，持续授权问题尚未解决。[最新反馈与候选方案复核](issue-review-20261030.md)说明官方 demo 的依赖、版本差异及验证边界。

### v0.2.52：原生 AutoAuth 恢复

v0.2.52 补齐原生 AutoAuth：保存独立恢复密钥与设备，现有会话失去资格或取码被拒时优先恢复；发送前标记密钥已尝试，新密钥先保存、后探测，避免断线重放或取消请求丢失轮换。新授权已用正式代码完成独立新连接恢复及取码，长期续期继续验证。详见[原生恢复记录](native-autoauth-recovery.md)，不将短时成功描述为 OAuth 或 30 天续期已解决。

### v0.2.51：旧会话 `-14` 与 OAuth 拒绝分层

v0.2.51 修复取码卡在旧会话 `-14`：保留原缓存，使用现有授权取得新票据，候选会话取码成功后才替换；失败不删原会话、不刷新凭据，且限制尝试频率。真实私有副本对照已复现旧缓存失败、新会话及再次复用成功。

OAuth 拒绝与协议会话分开处理：授权被拒但仍有可尝试的 PSK 或独立原生恢复材料时显示“需补授权”，停止重试旧凭据，尝试保留的协议会话及原生恢复。材料缺失或手动标失效后停止使用。清除失效 token，保留扫码时间，不将取码当成 OAuth 续期成功，也不自动恢复历史失效账号。具体范围和真实验证见[分层处理说明](credential-session-layers.md)。

### v0.2.50：不再因单独应用层 `-14` 删除共享会话

（这一段中关于接口测试区的说明移到了[控制台与账号管理](console-features.md#接口测试)。）

v0.2.49 修复 PCMgr 部分请求仍携带 YYB 身份的问题，并按原生路径拆分手机号请求。接口测试会显示当前渠道与能力限制；文章入口是未验证的兼容转发，公众号入口只生成授权 URL。旧授权曾在 Go 与本机官方 DLL 均返回 `20138/1`；重新扫码后，飞牛正式版本的取码、密钥和手机号响应已通过限定目标的真实复测，测试期间授权不变。旧构造在本次密钥对照中也成功，不能将此前失败全部归因于字段混用，或据此宣称长期续期已恢复。Windows 正式程序启动与飞牛部署均通过，详见[调用路径与实测范围](pcmgr-api-paths-20261029.md)。
