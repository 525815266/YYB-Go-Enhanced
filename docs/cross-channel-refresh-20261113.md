# 应用宝与手游助手互救复核（2026-11-13）

## 结论

“互救”不能实现为把手游助手的 `refresh_token` 直接送到应用宝刷新端点，或反过来把应用宝令牌送到手游助手端点。两条 OAuth 签发链属于不同业务线，令牌不能跨渠道兑换。

本次对同一微信编队的真实凭据做了最小化网关探测，三种跨路由组合均返回 HTTP 200、业务 `code=-109`，没有新的 `userInfo`、access token 或 refresh token：

| 发送的令牌 | 请求端点 | 结果 |
| --- | --- | --- |
| 手游助手 | 应用宝主刷新 | `-109`，无新凭据 |
| 手游助手 | 应用宝 `_auth` 刷新 | `-109`，无新凭据 |
| 应用宝 | 手游助手 `syzslogin` 刷新 | `-109`，无新凭据 |

因此不能复制另一成员的 token、修改 provider 后重试，也不能把这类响应记录成续期成功。

## 已实现的互救层

同一微信的应用宝、手游助手等渠道仍可绑定到一个 fleet。每个成员保留自己的登录凭据、协议会话、限速和熔断状态；主账号调用时调度顺序现在是：

1. 已知 `alive` 的成员；
2. 状态未知的成员；
3. 只有缓存协议会话的 `session_only` 成员；
4. 已明确失效的 `expired` 成员。

同一状态等级内继续使用进程内 LRU 分摊。某成员收到凭据拒绝、会话不可用、上游应用拒绝、登录预算耗尽或成员熔断时，调用转移到下一个成员；业务请求本身的明确裁决不会被跨渠道重放。

这就是可验证的“互救”：应用宝 OAuth 被官方撤销时，主账号可以继续使用仍健康的手游助手协议会话；手游助手失效时也可以反向使用健康的应用宝成员。它不会让失效的 OAuth 凭据复活，也不会伪造 `alive` 或 `renewed`。

## 42007 / 40030 边界

`-109` 只是网关包装码，服务会按已有规则追加一次本渠道 `check_login`。如果底层明确返回微信 `42007`、`40030` 等凭据拒绝，成员进入 `expired` 或保留可用缓存会话的 `session_only`。编队调度会避开它，但不会把另一渠道的 refresh token 当作修复材料。

如果编队所有成员都不可用，接口仍返回掉线/需要重新扫码的错误；这时必须重新授权对应渠道。短期 refresh 成功、同 token、延长本地期限或已有协议会话，都不能证明官方授权仍可长期保活。

## 验证边界

- 共享 `pcyyb_get_wx_login_buffer_auth` 对应用宝和手游助手凭据均能返回登录票据，证明两者共享 WMPF/ILink 协议层身份；这不是 OAuth refresh token 互换。
- 手游助手仍使用官方对应的 `syzslogin` 刷新与 check-login 路由。
- 本次改动只改变 fleet 选择顺序和故障转移行为，不新增真实业务取码、不写入生产凭据，也不宣称手游助手或应用宝获得 30 天长期保活。
