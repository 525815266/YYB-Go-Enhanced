- 该任务 2026-10-27 22:01 之前每轮约 10 个账号成功；**2026-10-28 00:01 起每轮 0 成功**，至今未恢复。10-27 22:40 前后的集中失效发生在上游（#105），与本项目代码和该脚本无关。

## 17:07 逐步对照实验（#4，17:06:29 刚扫码）

用京东任务会发的几种请求，在 #4 上逐步试，每步之间留 25 – 30 秒并探测账号是否还能取码：

| 步骤 | 结果 |
| --- | --- |
| 基线单次取码；25 秒后再取一次 | 都成功 |
| 0.3 秒内连发两次取码（同一 AppID） | 两次都成功，30 秒后探测成功 |
| operateWxData `getUserInfo`（withCredentials） | 成功，探测成功 |
| 京东护照 AppID（`wx2f5d8f9715c59d10`）取码 | 返回 `wx.login returned no code`（该 AppID 不是小程序，空 code），不是 `-14`；探测成功 |

结论：**这些步骤都没有立刻造成协议层的 `-14`；但每步之后的探测用的都是取码（协议会话），它们没有、也不能证明 OAuth 授权是否受影响。** #4 的 OAuth 授权后来在 19:03 被发现已吊销，吊销时刻无法确定，17:07–17:11 的这些步骤本身也不能排除，所以“单步不致命”不能成立。要判断授权是否受影响，必须直接看 OAuth 层（取票据、刷新、check-login）。京东任务的真实流程还多了这些差别：京东服务端会消费这些 code、对全部账号逐个循环、发生在偶数整点。

## 为什么还不是定论

- 12 次授权事件只涉及 5 个账号，不是 12 个独立样本。
- 恢复链在第一次取新票据之前，先做过一次保存票据的 ManualAuth（收到 `-10` 才取新票据），所以“#1、#4 第一次取新票据就被拒”只能排除其后的操作，不能排除这次保存票据登录参与吊销。
- 同一个 cron 不等于同一个请求序列：10-28 00:01 起京东 `login_lt` 不再返回 pt_key，任务从“每账号一次取码”变成“多次取码 + getUserInfo + 护照 AppID 取码”的回退分支，请求序列在那一刻变了，这可能是“以前没事、现在出事”的原因之一。
- 样本是 10 次失败和 1 次奇数点存活；16:00 这一轮京东任务照常运行（计划中的“停用”并未生效），所以仍没有“停用后”的对照。
- 同一整点还有其他任务：每小时的「青龙更新监控」、14:00 的积分任务、16:00 的「移动云盘」等，不能仅凭时间排除。
- 腾讯侧也可能有按整点的清理；本项目无法从日志区分。
- 取码返回 `-14` 的究竟是哪个 AppID、哪类请求，v0.2.59 及之前的日志没有记录。

## 对照实验

1. 在偶数整点之前停用该任务，让新扫码的账号至少经过一个偶数整点，观察是否仍在整点后失效。
2. 存活：说明该任务或它的调用方式是触发因素；仍失效：触发在别处，不要继续围绕该脚本投入。
3. 若存活，再单独让该任务只处理一个牺牲账号，逐步确认是 `getCode` 的第二次请求还是 `operateWxData` 触发。
4. 续期：存活的账号到约 1 小时 56 分时应出现 `keepalive.renewed`，同时验证续期本身是否工作。

读取方式：运行日志中 `account.scanned` 之后首次 `protocol.failed` 的时刻。v0.2.60 起事件带 `app_id` 和 `operation`（`get_code` / `get_phone_number` / `operate_wx_data`，operateWxData 另带 `api`），可以直接看到被拒的是哪个 AppID、哪类请求。

## 给第三方脚本的建议

- 被 `502` / `429` 拒绝后，不要立刻再请求一个新 code，也不要改走 `operateWxData`。
- 连续 3 个账号遇到 `502` / `429`（`409` 是本地已失效，不计）就中止本轮。
- 只处理需要的账号，不要遍历面板里的全部账号。
- 把整点任务错开并加随机抖动。
- 本服务 v0.2.59 起对反复被拒的目标返回本地 `429` + `Retry-After`，脚本应据此退避。

## v0.2.60 与本问题相关的改动

- 事件日志记录 `app_id` / `operation` / `api`，不记录 payload。
- 会话刚验证成功（2 分钟内同账号同出口已有请求成功）时，取码 `-14` 不再触发票据 + ManualAuth 恢复。
- 熔断按请求类型区分，取号 / operateWxData 被拒不再拦住同 AppID 的取码。

这些改动降低“被拒后继续追加登录和请求”的放大，**不保证**授权不再被吊销。按 16:00 的时间线，吊销多半发生在恢复之前，所以“会话刚验证成功不再重登”预计救不了这类账号，价值主要是少追加登录请求。
