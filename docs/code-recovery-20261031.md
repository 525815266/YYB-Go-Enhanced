# v0.2.55：恢复取码重建顺序

#118 有多位反馈者确认回退 v0.2.49 后取码恢复，也有人仍发生失效。这是必须处理的版本回归线索；成功取码本身还不能证明后台 OAuth 续期成功。

## 确认的代码差异

固定合成输入对照 v0.2.49 / 50 / 51 / 52 / 54：两个渠道各自的 js-login、ManualAuth、会话头及归一化随机设备后的资料 / 手机号业务字段未互换。恢复路径则有以下差异：

| 路径 | 旧行为 | v0.2.55 |
| --- | --- | --- |
| 有效授权，旧会话取码应用 `-14` | v49 重建保存票据；v50 停止重建；v51 优先取新票据；v52 起优先 AutoAuth，失败即退出 | 先尝试同渠道保存票据，新候选对相同 AppID 取码成功后才写回 |
| 保存票据 ManualAuth `-10` | 恢复包装器可能挡住 HTTP 层合法兜底 | 取一次新票据，登录、验证后提交；保留各阶段错误 |
| 新票据明确 access 拒绝 | 通用恢复包装器直接返回 | 仅明确类型允许一次凭据刷新；先保存新凭据，再取新票据和重试 |
| 自动恢复退避 | 账号与出口共享五分钟，成功也占用窗口 | 失败按账号 / 出口 / AppID 退避；成功解除，过期记录清理 |
| `session_only` | 不得使用已拒的 OAuth / 保存票据 | 保持限制；只能复用缓存或使用未消费的独立原生材料 |

手机号、数据操作没有加入新的应用 `-14` 重放。网络失败、空 code、普通 PCMgr 票据业务 `1` 不构成 access 失效证据。授权变更、手动失效、代理不同或候选无 code 时，不提交旧结果。正常后台续期时机不变。

## 验证与限制

离线回归覆盖保存票据直接成功、`-10` 后新票据成功、网络失败不刷新、目标拒绝不升级为主授权拒绝、明确 access 拒绝的一次凭据刷新、先保存轮换再重试、取消、原缓存保留、跨目标退避、重扫和并发密钥轮换防覆盖。正常授权缓存缺失时不抢先消费 AutoKey。

10 月 31 日新 YYB 授权在维护环境 v0.2.54 上首次取码 HTTP 200，授权与扫码基准不变；该成功发生在补丁部署前，不能记为补丁修复成功。此前授权已进入 `session_only`、保存票据已清空，不用旧授权伪造完整49版对照。正式版本部署及后续真实请求结果另行追加。

本地保留旧缓存不保证候选登录后上游仍接受旧会话；候选握手本身可能改变服务端状态。新授权首次成功、同 token 响应、缓存期限或短时取码均不等于自然长期续期。需要结合正常刷新日志、凭据到期前移、扫码不变及原到期后的真实取码继续验证。已清空的票据不能凭补丁找回，需要重新扫码。
