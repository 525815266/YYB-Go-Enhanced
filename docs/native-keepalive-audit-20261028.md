## 已确认的账号续期流程

| 环节 | 官方实现 | 证据 |
| --- | --- | --- |
| 定时检查 | 每 120,000 ms（2 分钟）检查一次 | `AndrowsSvr.exe` 的 QTimer 设置及 timeout 回调连接 |
| 续期时机 | 当前时间 + 240 秒达到 expireTime 时尝试刷新 | `CLoginService::OnCheckRefreshToken` 中的时间比较与分支 |
| 主登录续期 | POST `/pc_yyb/pcyyb_refresh_token`，业务 `pc_yyb` | 原生 `CLoginBackend::RefrashToken` 与官方网页 `fetchRefreshTokenApi` 相互印证 |
| 登录核验 | POST `/pc_yyb/pcyyb_check_login` | 原生 `FetchCheckLogin` 与官方网页 `featchCheckLoginApi` |
| wxapp 独立授权续期 | POST `/pc_yyb_auth/pcyyb_refresh_token_auth`，业务 `pc_yyb_auth` | 官方网页 `refreshWxTokenV3Api`，独立检查 wxappExpireTime |
| 获取协议登录票据 | POST `/pc_yyb_auth/pcyyb_get_wx_login_buffer_auth` | 官方网页 `fetchWxGameLoginBufferApi`，与项目已有接口一致 |

这不是每两分钟都刷新一次 token。客户端每两分钟检查到期时间，只有进入提前四分钟的窗口才发送续期请求。其具体发起时间会受定时器相位、进程休眠和网络影响。

两个续期接口的请求体均包含 `userInfo` 下的 `openId`、`accessToken`、`refreshToken`、`loginType`；业务标识与签名配置不同。官方公开网页请求封装对实际 JSON 请求体、毫秒时间戳、业务 accessKey、nonce 求 MD5，与项目已有签名算法一致。不能只替换 URL 而沿用另一业务的签名配置。

### ILink 设备标识的进一步定位

继续分析真实运行库，已把 `GetAppDeviceId` 定位到 `ilink2.dll` RVA `0x1783d0`：读取 INI 配置中的 `AppDeviceId`，非空时直接返回，空值分支生成并转换为十六进制后执行 `ini_file::set` 与 `commit`。这确认该网络层标识会持久保存，而非仅有相关字符串。

继续追踪直接调用者后，增加了比符号关联更具体的证据：`0x10318c` 调用 `GetAppDeviceId`，随后复制返回字符串到 `AppBaseRequest`；`0x1032c9` 将该对象放入当前构造的 `ManualAuthRequest`。构造函数与 MSVC RTTI 相互核对：`0x145e10` / vtable `0x7e96b0` 为 `ilinkcliproto::AppBaseRequest`，`0x146470` / vtable `0x7e9718` 为 `ilinkcliproto::ManualAuthRequest`。缺省生成分支在 `0x178595` 生成 8 字节，再转十六进制字符串并持久保存。这确认持久设备标识确实进入登录请求对象，不再只是网络层存在一个同名配置。

项目当前 `randomAppDeviceID()` 每次握手生成 32 个原始随机字节，与以上持久化行为有差异。后续继续解析确认官方 TDI 应用登录另有 `kTdiKeyDeviceId`，缺省也生成 32 原始随机字节并持久化；不能把网络内部 16 字符分支当成全部官方登录的默认格式。两种设备配置、原生位置及隔离实测见[补充对照](native-wire-layout-20261029.md#两套设备标识与-tdi-thirdapp-分支)。没有证据证明长度差异导致 OAuth refresh token 被撤销；票据设备与请求头设备的来源也不能混用。v0.2.40–v0.2.43 均未据此更改生产设备字段。
