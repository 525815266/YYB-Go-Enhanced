# 雷电重扫身份轮换修复

## 现象

雷电游戏中心每次扫码都通过一次性 login ticket 换取新的 `login_buffer`。项目原先把 ticket 的摘要写成 `ldplayer:<id>`，所以同一微信再次扫码时 OpenID 必然变化。旧的多渠道更新逻辑只在成员已标记为 `expired` 时允许替换；成员仍是 `alive`、`session_only` 或 `unknown` 时会提前返回 409，扫码页无法继续确认，也无法更新原账号。

## 处理规则

- 雷电组内已有同渠道成员且新 ticket 身份变化时，服务端返回结构化的 `identity_confirmation_required`，二维码会话保持有效，等待操作员确认“同一微信”。
- 确认后在事务内原位替换该成员的 OpenID、login buffer 和凭据，保留原数字 ID、fleet 归属、备注和配置；不会新增账号。
- 未确认不写账号、不消费链接、不激活新会话。组内已有多个雷电成员时拒绝自动猜测，要求先在控制台整理。
- 事务仍检查链接归属、主账号锚点、成员归属、重复身份和并发快照；确认不能覆盖另一个已存在的相同 OpenID。

## 渠道身份边界

应用宝、电脑管家、腾讯手游助手和 QQ 浏览器提供可用于冲突判断的账号字段，继续执行原有同渠道身份及可比较 UnionID 校验。雷电没有稳定的跨重扫身份字段，因此只接受显式人工确认，不以昵称、头像或 ticket 摘要推断同一微信。

本次改动只解决雷电重扫的归组和原位更新，不改变协议请求、票据生成或保活算法，也不证明雷电授权能够长期自动恢复。新 ticket 仍可能在上游撤销后要求再次扫码。

## 验证

合成回归覆盖雷电成员状态 `alive`、`session_only`、`unknown`：未确认保持原记录不变，确认后记录数不增加、成员 ID 和 fleet 保留而票据身份更新。全量 Go 测试与静态检查作为发布前门禁。
