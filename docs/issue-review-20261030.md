## 游戏中心候选（#117）

反馈目前只有文字，没有实现地址、接口、脱敏调用链或可复核记录。现有服务已区分 YYB / PCMgr 两条扫码及协议通路，但同一微信身份不等于两个互不干扰的独立授权环境。

PCMgr 静态调用者已确认可转交给已登录的桌面微信并跳过 WMPF 登录检查，详见[官方状态及启动通路](pcmgr-official-state-20261030.md)。这使“官方业务页面能打开”和“独立协议 code 持续有效”必须分开验证；也不能反过来断言所有游戏中心场景都走此分支。保持窗口打开是否触发了有效续期，仍需真实调用事件证明。暂不以此上线“无限保活”开关。

## 新日志按账号和授权分段（#112 / #114 / #115 / #118）

- #112 的 `09:31:50 pcmgr_login_buffer/6` 属于扫码前旧账号 3。新账号 1 于 `09:35:06` 扫码，`09:35:23` 成功取码，`09:39:04` 实际错误链为 `shortlink_application/-14 → native_autoauth_business/-13`。不能把旧账号的 `6` 拼成新账号同一次恢复的第三层，也不能把认证后的业务拒绝视为请求各字段必然完全正确。
- `09:39:04` 距上次成功 3 分 41 秒，距扫码 3 分 58 秒。两次请求只给出了成功和失败的采样点，不代表精确失效时刻或固定有效期。青龙请求是观察到失败的触发点，尚无证据认定该脚本撤销了授权。
- `09:41:05 recovery_deferred` 符合五分钟退避，没有再次发送 AutoAuth；本次仅返回原始 `-14` 不表示此前的 `-13` 消失或已修复。
- #114 / #118 的混合链已实际进入 AutoAuth 并被业务层拒绝，不能回复成“恢复代码没有执行”，也不能仅凭这些码确定代理不稳定或上游撤销的具体原因。
- #115 的单独 `-14` 仅说明当前应用请求被拒绝。`alive`、名义到期时间或本地 PSK 可解析，均不是此时业务成功的证明；同样也不足以判定必须清空整个账号。

`request_rejected` 的现有定义是**整个错误链仅为应用请求拒绝**，供账号级恢复保护使用。混合 `-14/-13` 为 `false`，不表示取码没有被拒绝，也不表示业务成功。它不是“错误链中是否出现过任意拒绝”的布尔值，排查应读取 `upstream_errors` 和相应恢复事件。本轮明确这一语义，不为修正文案改变恢复判定函数。

## “v0.2.46 正常，升级后失败”的对照（#118）

已对比 `v0.2.46..v0.2.53` 的 `pool.go`、`ilink.go`、`shortlink.go`、取码恢复和 HTTP 调用层：

| 项目 | v0.2.46 | v0.2.53 |
| --- | --- | --- |
| YYB 首次 js-login 构造 | `buildJSAPIPlaintext` 后加密传输 | 同一构造函数和请求字段；新调用 helper 将空 code 明确作为错误 |
| PCMgr | 尚未正式加入双渠道产品能力 | 独立 host、扫码及渠道 API 路径；不能用 v0.2.46 的 YYB 结果代替 PCMgr 对照 |
| 单独应用 `-14` | 作为 payload 类错误，可删除共享会话并用旧票据重建；后续可能进入账号凭据恢复 | 保留原请求错误；取码优先原生恢复，否则取新票据并验证候选；失败不会仅因应用拒绝清空账号 |
| 原生密钥 | 未保存独立恢复材料 | 保存设备 / AutoKey / EncKey，同出口 CAS 标记尝试并持久保存轮换，禁止重放不确定请求 |

因此升级改变了恢复行为，反馈必须保留为回归线索；但日志中的原请求 `-14` 出现在恢复 `-13` 之前，不能把新增错误文字单独当作首次失效由新版造成的证据。也不能排除新增握手影响后续上游状态。现有材料不足以确定回归根因或承诺回退有效，需要同一渠道 / 目标 / 出口以及首次失败前后的授权时间线。不建议通过生产降级、清库、连续重扫或重放已尝试密钥制造对照。

## 页面切换与接口拒绝的追加对照（#112 / #118）

以下时间均为北京时间 2026-10-30，报告区分反馈者现场、合成浏览器复现及维护环境真实请求，未公开授权、账号身份或原始日志。

### 已复现并修复的页面上下文重置

#118 新增反馈称“我的控制台”失败而“我的微信”成功。两个入口实际使用同一个模板和 `/wx/code`，但旧侧栏跳转会重新加载文档并丢失 `ref`：合成的两个不同渠道账号中，选中第二个并填写目标后切换，下一次请求实际变成了第一个账号和默认 AppID。因此页面结果不能直接作为同账号 / 同目标的协议对照。

v0.2.54 将三个工作台入口改为同文档导航，保留选中账号、AppID、能力、请求正文和结果；历史前进后退同步 URL 所指账号，没有 `ref` 的初始入口回到默认首个账号。令牌只保存在当前文档内存，刷新仍清空，未写入 URL / localStorage / sessionStorage。修改键点击和其他页面保持普通跳转。

`tests/workspace-navigation-ui.cjs` 使用合成账号与本地资源，1440 / 390 像素浏览器验证切换前后请求一致、历史账号恢复、进行中请求不重复、令牌仅在内存、手机菜单关闭和无 JS 异常。该复现证实页面缺陷，但尚未证实它能解释反馈者全部现象，更不能将修复等同于上游授权恢复。

### 真实旧会话请求仍然失败

17:10–17:13，维护环境 v0.2.53 的现有 PCMgr 授权分别执行一次控制目标取码，再对照控制目标 `/wx/code`、君品荟 `/wxapp/getCode` 数字引用与 `/wx/code` 保存身份引用。四次均 HTTP 502、无 code，仅 `shortlink_application/-14`；扫码时间、凭据摘要、会话更新时间和原生密钥尝试时间均未变化，没有新增 AutoAuth。此样本不能复现“换页面即可成功”，也不是 YYB 渠道回归的同条件证据。

保留已存在的 13:00、13:15 正常新票据恢复成功事件，以及 13:08、14:00 原生恢复业务 `-13` 失败事件。名义 PSK 期限未到不能证明真实业务可用；外部正常请求持续到达，不能仅凭同时发生认定某个脚本撤销授权。未停止其他任务、提前续期或重放旧 AutoKey。

### 尚待验证的请求差异

- #112 最新 YYB / 小米反馈及截图确认 `/wxapp/getCode` 先 HTTP 200，约一秒后 `/wxapp/operateWxData` 为 502 / 应用 `-14`；截图未给出精确 `api_name` / JSON 结构或后续控制取码，尚不能认定整个账号失效。目标小程序的资料授权与 `/wx/getuserinfo` 渠道资料是不同接口。
- #118 “legacy JSONDecodeError”发生在首次 YYB 502 之后，属于调用脚本回退解析失败，不能覆盖或解释首次 `-14`。单独 `-14` 与混合 `-14/-13` 继续分别记录。
- 同一评论随后引用“传输一次失败即无锁、无条件刷新”的推断。当前 `invokeWXApp` 对超时、取消、网络错误及 EOF 直接保留原错误，不进入凭据刷新；单独应用拒绝 / 取码恢复错误也提前返回。凭据刷新按账号加锁，后台检查有效期与提前量，写回核对授权快照；其他已分类错误仍可能进入强制恢复。已有网络失败不刷新 / 不丢会话、等待锁可取消及并发扫码不覆盖回归，不能把这段概括直接当成当前根因，也不能据此排除尚未定位的其他恢复缺陷。
- 旧授权控制取码已失败，因此先请求更新同渠道授权，未重复发送已尝试的旧恢复密钥。用户随后更新 PCMgr，17:29:58–59 完成控制取码 → 小米取码 → `webapi_getuserinfo` → 小米再次取码 → 控制复测，均 HTTP 200；四个取码为 32 字符 code，资料业务 `err_no=0`。资料请求使用 `data={}`、`env=1`、`with_credentials=true`，不是反馈者尚未提供的原始 JSON。扫码、凭据与会话在序列内不变，没有触发原生恢复。这是新授权即时正结果，尚未复现对方问题，也不能替代 YYB / 精确原请求及延时对照。

本版只修复可复现的导航问题，未更改握手字段、账号状态、恢复条件或后台续期策略；#112 / #118 保持开放，持续授权与 30 天保活尚未验证解决。
