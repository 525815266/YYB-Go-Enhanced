# 任务高峰与取码限速（2026-11-02）

这篇记录一次对照实验和随后加入的每账号取码限速。结论分两层写：已经观察到的事实，和仍然只是推断的部分。

## 观察到的事实

**1. 没有任务触达的授权撑过了第一次续期。** 11-01 晚上用两个独立微信号各扫了一个授权，放在两个没有接入青龙任务的试验实例里：

- 新版代码，提前量设为 45 分钟：扫码 23:18:28，`keepalive.renewed` 在 00:33:47，到期时间后移 2 小时。
- 旧版代码，30 分钟检查、45 分钟提前量：00:35:14 日志出现 `credentials renewed`，到期时间同样后移 2 小时。

两个都至少撑过了 75 分钟，期间没有任何取码请求。

**2. 接入青龙任务的授权在任务高峰里失效。** 正式环境里重扫的两个授权：

- 账号 1：23:59:53 扫码，00:19:24 到 00:19:31 的 7 秒里连续成功取码 12 次（不同的小程序），00:19:32 的恢复流程发现所有层都被拒（`login_buffer -101 / 42007`、`refresh_token -109`、`check_login -109 / 42007`），状态变为 `session_only`。
- 账号 18：23:08:08 扫码，00:22:56 起的 18 秒里连续发生 10 次“重新登录 + 取码”，前 9 次成功，第 10 次（00:23:14）起所有层同时被拒。它最后一次成功的恢复在 00:23:13，所以失效时刻被夹在 2 秒窗口里。

**3. 高峰的来源是青龙里的任务。** 青龙共有 414 个任务，大量是 `*_code版.py`，每个脚本读取 `YYB_SERVER` 里的 `地址@账号` 逐个账号取一次 code，用各自的 AppID；多数设在 `19 0 * * *`，00:19:01 同时启动。00:00 到 00:25 正式环境收到 2576 次取码请求，其中 409（账号需重扫，本地拒绝）1450 次，429（熔断，本地拒绝）786 次，502 292 次，200 44 次。重扫的账号沿用原来的编号，所以原有的任务配置立刻就会对它们取码。

**4. 此前的结论需要更正。** 11-01 晚上停用两个京东任务后，我把正式环境账号当作“没有业务调用”的对照，这是错的：其余任务一直在访问它们。真正没有任务触达的只有上面两个试验实例。

## 仍然是推断的部分

- 上面是强相关，不是证明：账号 1 的授权在 00:19:32 才第一次被检验，它可能更早就已经失效；账号 18 的 2 秒窗口则说明失效发生在连续恢复期间。
- 不知道是哪一类流量起作用：取码频率本身、同时登录大量不同小程序，还是连环恢复（每次恢复都是一次新的登录票据请求）。v0.2.59 的事件不记 AppID，无法区分；v0.2.60 起事件带 `app_id` 与请求类型。
- 没有验证过限速后授权能活下来，也不知道安全速率是多少。

## 版本关系

- v0.2.60 加入“会话刚验证成功时，`-14` 不再触发重新登录”。账号 18 失效前的 10 次连环恢复，正是这个防护要避免的。
- v0.2.61 加固这个防护（标记绑定到会话本身，只有非空 wx.login code 才算验证），并加入下面的限速。

## 取码限速（v0.2.61 起）

熔断只在失败之后起作用，一连串成功的请求不会触发它。限速补上这一块：每个账号向上游发出的请求按固定间隔排队，排不进的请求立刻本地拒绝。

- 每个账号的请求依次占用时间槽，相邻两个槽至少隔 `YYB_CODE_MIN_GAP`（默认 `2s`，相当于每分钟最多 30 次）。
- 槽距现在超过 `YYB_CODE_MAX_WAIT`（默认 `20s`）的请求不排队，立即返回 HTTP `429`（带 `Retry-After`，`data.circuit_open` 为 `pacing`），不访问上游，也不改变账号状态。
- 账号之间互不影响，空闲账号的第一个请求马上执行。
- 取码、取号、operateWxData 共用同一个队列（面板里的取码测试也走它）；续期、扫码、账号管理不受影响。
- 一个突发只记一条 `protocol.paced` 事件（`waited` 排队数、`refused` 拒绝数、`duration_ms` 统计窗口），不会每个请求一条。
- 设为 `off` 或 `0` 关闭。

数据库目录里的 `tuning.json` 可以在不重启的情况下覆盖这两个值，一秒内生效：

```json
{"code_min_gap_ms": 2000, "code_max_wait_ms": 20000}
```

缺少的键沿用默认值，`0` 表示关闭限速，文件无法解析时保留上一次的有效设置，删除文件则恢复默认。

这会让高峰时段里排不进的任务拿到 429 而失败。更根本的办法是在青龙里把任务错开，而不是让几百个任务在同一分钟取码。

## 怎样验证

重扫账号后，观察它在青龙的高峰里能否撑过。运行日志里：

- `protocol.paced`：限速是否生效、拒绝了多少；
- `protocol.recovery_started` / `ticket_requested`：重新登录是否还在连环发生；
- `account.expired`、`keepalive.failed`：授权是否仍然被拒。

如果账号仍然在限速后失效，说明速率不是主因，需要根据带 `app_id` 的事件继续缩小范围。
